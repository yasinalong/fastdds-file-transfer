# file_transfer 使用说明

安装和依赖准备见[仓库首页](../../README.md)。

## 使用


在仓库根目录构建：

```bash
./scripts/build_apps.sh release --target file_transfer
```

接收设备 A、B 分别启动；保存目录由各自设备配置，文件名沿用发送文件的原名：

```bash
# 设备 A
./out/apps/release/bin/file_transfer receive --output out/received-a --domain 42 --topic files
# 设备 B（本机演示时也可以在另一终端运行）
./out/apps/release/bin/file_transfer receive --output out/received-b --domain 42 --topic files
```

发送设备执行一次：

```bash
./out/apps/release/bin/file_transfer send /path/to/photo.png --domain 42 --topic files --receivers 2
```

两端得到各自目录下的 `photo.png`。`--receivers 2` 要求发现至少两个接收端；省略时，选择发现窗口内响应的全部接收端。
正常轮次名单在发文件前固定；发送进程运行期间中途加入的节点进入后续补发轮次，同一起点共享补发 Topic。
每轮开始后不再加入新节点，进程完成即退出，不等待未来节点。发送端输出每个接收端的 ID、完成状态、续传起点和确认字节数；
只有本批全部接收端完成，总结果才是 `COMPLETED`。一端失败，其他端继续接收，总结果报告失败或未知。

断线、取消或进程重启后，重新执行同一发送命令即可续传，无需提供偏移或旧任务 ID。
接收进程重启后，仍在线的发送进程也会重新协商并恢复；恢复过程须在配置的超时内完成。
接收目录里已有同名且 SHA-256 相同的完整文件时直接确认成功，不再发送该端需要的文件数据。
同名不同内容不会覆盖。同一目录内同名任务或相同内容的并发写入互斥，完成后可重试。

## 常驻接收与超时

接收端处理完文件继续监听，单文件失败、取消、传输超时都不会关闭服务。
`--idle-timeout 60` 表示连续 60 秒没有发送端在线才退出；默认 0 永久监听。
任一发送端上线就清零倒计时，最后一个发送端离线后重新计时。在线但暂时没有文件流量不算无人在线。
异常断网/崩溃的离线识别依赖 DDS 发现租约（当前默认约 20 秒），之后才开始空闲计时。

`--timeout` 限制发现、准备、持续写入背压、最终结果等待和节点失联；接收侧另按实际数据追加判断无进展。
默认 30 秒，慢磁盘、大文件恢复校验或异常网络可适当增加。
源文件在传输期间必须保持不变；发送端检查长度和修改时间，最终内容仍由 SHA-256 验证。
首次发送前需读取整个源文件计算哈希；重启续传需读取已有前缀进行校验，不承诺大文件瞬时开始发送。

## 断点与落盘

接收目录内仅增加一个工作目录：

```text
out/received/
├── .file_transfer/
│   ├── receiver.id                 # 稳定接收端身份，同时锁定此保存目录
│   └── <文件 SHA-256>.part         # 尚未完成的文件内容
└── photo.png                      # 校验、提交成功后才出现
```

- 每块直接写入 `.part`。有写入时，每累计 4 MiB 或距上次同步超过 250 ms 执行 `fsync`；提交前再次同步完整文件。
- 部分文件的长度就是待校验的恢复位置，不保存独立进度表。恢复时重算已有前缀哈希，发送端与源文件对应前缀比对；不一致则清零重传。
- 正常端共享从零开始的顺序数据流，发送位置不回退。有断点的接收端进入恢复队列，正常端结束后按相同起点分组，共享 Topic 从已验证偏移传到末尾。
- 传输中重启或出现应用层缺口的接收端退出正常订阅，转入恢复队列；不参与本轮的端不接收补传数据。恢复端不会重新加入本批公共流。
- 整文件 SHA-256 一致后，以不覆盖目标的方式原子发布文件名，同步目标目录，再删除部分文件。提交不确定时允许再次协商确认。
- 取消、超时、写失败和进程退出都保留部分文件；最终哈希错误会清零损坏内容。断电可能损失最后未同步部分，恢复时必须重新验证，不能盲信长度。
- 准入时检查剩余文件所需空间，写入时保留约 16 MiB 余量；外部程序竞争磁盘仍可能导致写失败，届时保留已有进度并报告具体原因。

不要复制 `receiver.id` 给另一台接收设备。一个保存目录只允许运行一个接收进程；复制后的设备应使用独立的新保存目录。
不再需要续传的 `.part` 可以在停止接收服务后手动删除。程序不自动删除未完成文件，因此应管理长期未完成的缓存占用。

## 参数

```bash
./out/apps/release/bin/file_transfer --help
```


| 参数                        | 默认                           | 含义                                                                      |
| --------------------------------------- | ------------------------------ | ------------------------------------------------------------------------- |
| `--domain`                              | 42                             | 两端相同，0～232                                                          |
| `--topic`                               | files                          | 两端相同，1～64 个字母、数字、下划线或连字符；兼容`--channel`             |
| `--transport`                           | tcp                            | 两端相同；支持`tcp`、可靠 UDPv4 `udp`、实验性 `udp-multicast`             |
| `--multicast-group`                     | 239.255.0.2:(7401+250×domain) | 接收端，仅`--transport udp-multicast`；同一轮次的接收端须相同，端口可省略 |
| `--timeout`                             | 30                             | 秒；阶段等待、持续背压、节点失联和接收无进展期限                          |
| `--receivers`                           | 0                              | 发送端，至少等待多少接收端；0 表示发现窗口内全部，最多 64 个              |
| `--discover-ms`                         | 2000                           | 发送端，首个接收端响应后的发现窗口，0～10000 ms                           |
| `--chunk-bytes`                         | 262144                         | 发送端，1 KiB～256 KiB                                                    |
| `--output`                              | out/files                      | 接收端保存目录，无需文件名                                                |
| `--idle-timeout`                        | 0                              | 接收端，无发送端在线的连续秒数；0 永久监听                                |
| `--max-transfers`                       | 8                              | 接收端同时处理的文件数，1～64                                             |
| `--max-bytes`                           | 1099511627776                  | 接收端单文件限额，默认 1 TiB；0 只接受空文件                              |


| 退出码 | 含义                                                     |
| ------ | -------------------------------------------------------- |
| 0      | 所选接收端全部成功；或接收服务正常停止/空闲退出          |
| 1      | 有接收端失败，或启动/发现失败；逐端结果保留已成功信息    |
| 2      | 提交前取消，部分文件保留                                 |
| 3      | 提交结果未知，可能已有接收端完成；重试命令会核对已有文件 |

## 传输方式

默认 `--transport tcp`，两端必须选择相同方式。`--transport udp` 使用可靠 UDPv4。
`--transport udp-multicast` 为实验性组播模式，同一轮次中至少两个接收端宣告相同组播地址时可共享组播数据，单个接收端可能退回单播。
组播仅用于同一子网，依赖交换机、路由和无线网络的支持。组播模式下，未订阅某个文件的设备也可能在网络层收到组播报文。

## 运行要求与限制

- 面向受信任局域网，未实现身份认证或传输加密。
- 文件系统需要支持 POSIX 文件锁、硬链接及同步操作；当前源码面向 macOS / Linux，未适配 Windows。
- 仅支持普通、可定位、长度已知的文件，不支持目录同步或跨子网发现配置。
- 文件名最多 255 字节，不接受路径分隔符、点目录和控制字符。
- 文件 I/O 为同步操作，异常存储可能阻塞接收循环；同步持久性取决于文件系统和设备。
- 收发双方使用相同版本构建，协议暂不承诺跨版本兼容。
- 一对多 TCP 传输的发送出口流量随接收端数量增长，慢端仍可能影响吞吐。
